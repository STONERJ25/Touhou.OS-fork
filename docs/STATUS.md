# Status

Fork of TouhouOS without the learning-first constraints: the goal was to take the OS as far as one autonomous run
allows. Everything below is in the tree and covered by `python tests/run_all.py` unless it says otherwise.

## Build, run, test

```powershell
python tools/build.py                      # loader + kernel + userland + initrd + build/esp
.\tools\run-qemu.ps1                       # interactive window, serial on this terminal
python tools/mkimage.py                    # bootable GPT disk image for a USB stick: build/touhou-os.img
python tests/run_all.py [name]             # the scripted QEMU tests (optionally only those matching name)
python tools/qemu.py boot --until "Welcome to Gensokyo" --shot build/shot.png    # headless boot + screenshot
$env:TOUHOU_CPU = "Skylake-Client-noTSX-IBRS"   # optional: run QEMU as a Skylake/Kaby Lake CPU instead of `-cpu max` (the real target is an i5-7500)
```

Needs (all installed on this machine): LLVM/Clang 22 (clang, ld.lld, lld-link, llvm-objcopy, llvm-ar), NASM, QEMU 11
(bundles OVMF), Python 3.13 with Pillow/numpy. `tools/dev-shell.ps1` adds them to PATH for manual use. Building on Linux:
[LINUX.md](LINUX.md). Using the desktop, the shell and the files: [USER_GUIDE.md](USER_GUIDE.md).
Running on a real PC: [REAL_HARDWARE.md](REAL_HARDWARE.md); what was reviewed for it, what was fixed and what can only be checked on the
machine: [HARDWARE_AUDIT.md](HARDWARE_AUDIT.md).

## Known issues / next

- Only one CPU is used (the other cores are idle); everything is polled.
- Only a mounted HUMANVILLAGE volume persists: it holds the homes and Keine's records, the `/etc` files that are kept across restarts (passwords, accounts, host name, time zone, `network.conf`, `update.conf`; [PERSISTENT_ETC](PERSISTENT_ETC.md)). Without such a volume `/etc` and the homes live in RAM and are rebuilt at boot.
- USB mass storage is in (bulk-only sticks, [USB](USB.md)): the stick the OS booted from carries `/HumanVillage`, and the kernel log is kept on it
  (`TOUHOU.LOG`, [REAL_HARDWARE](REAL_HARDWARE.md)). A stick flagged dirty is gone through before it is mounted (read-write when nothing is out of place; read-only with
  the reason in `/proc/fatcheck` otherwise; `hvforce` / `hvcheck=off`, [STORAGE](STORAGE.md)). The FAT write order is safe against power cuts (six flush classes, tested with random
  cuts: lost clusters at worst; STORAGE.md "Write ordering"). Not covered: UAS; `fsck` (written, host-tested, **not yet run in the guest** until the `fsck` agent reports:
  see "State when paused" in STORAGE.md). On the Dell the boot stick worked as `/HumanVillage` with `TOUHOU.LOG` ([HARDWARE_AUDIT](HARDWARE_AUDIT.md)).
- The target PC (a Dell OptiPlex, Core i5-7500) booted this OS to the desktop on 2026-10-23: the screen (write-combining, about 9 GB/s), USB keyboard and mouse behind a hub, the USB stick as `/HumanVillage`, `TOUHOU.LOG` and a clean shutdown all work; its first log and what it showed are in [HARDWARE_AUDIT](HARDWARE_AUDIT.md). Sound works there too (the owner heard `beep` through the speakers, see NEXT). Since then (2026-10-24/25): the internal NVMe disk is read (AHCI mode now), the network works (DHCP, ssh from the dev PC), the install onto the disk has not been done. A slow screen would correct itself (a write-combining MTRR fallback), and the audit has the first-boot checklist.
- Job control: the kernel side exists (stopped state, Ctrl-Z, `waitpid` with WUNTRACED, orphaned groups; [JOBCONTROL](JOBCONTROL.md)), but gapsh does not use it yet: its `jobs` and `fg` only know background jobs that are running, `bg` only prints the job, and the shell half is not started (task 6 in the cloud agents' task list), so for now Ctrl-Z freezes the foreground job and the shell prompt along with it.
- The local agent log (`docs/AI_SUMMARY.md`, gitignored) has the newest development notes.
