# Running Linux (and later Windows) programs: the plan

**Goal, very far out:** run unmodified Linux programs on TouhouOS, and after them Windows programs, with Windows-era games as the benchmark. This page is the plan for the Linux half (Windows comes after it and will get its own page), the rules the work follows, and what was measured before any kernel code was touched.

## The rule: original code, from specifications and from behaviour

The project's other large parts (TLS, TrueType, the web engine, the JavaScript engine, the C compiler) were written from public specifications with no code taken from other projects. The compatibility layers follow the same rule, on purpose, even though it costs more: a ground-up layer fits the kernel it lives in, and the kernel is still young enough to shape both together.

* **Allowed sources:** public specifications and documentation (POSIX; the Linux man pages as documentation; the System V x86-64 psABI; the ELF specification; the Intel and AMD manuals; the PE/COFF specification and Microsoft's public API documentation), and the **observed behaviour** of real systems, measured with our own test programs (a Linux under WSL on the development PC; the owner's Windows).
* **Not allowed:** reading or copying the source of the Linux kernel, glibc, musl, the BSDs, Wine, ReactOS, Mesa, SDL or any other implementation of what we build.
* **Test inputs are not code we ship.** Third-party Linux programs (a busybox, Python, a distribution's `ls`) are inputs to tests, never part of the tree. A dynamic glibc or musl program needs *its own* dynamic linker and libc files at the paths it names: those are data the user provides in a Linux root directory, not something we write or ship.
* **Struct layouts, constants and numbers** come from the psABI and the man pages and are *verified by oracle programs*: a C program built on a real Linux prints `sizeof`/`offsetof`/values, and its output is stored as a test vector (facts, not code).
* **Behaviour is pinned by differential tests:** the same small program runs on real Linux (WSL) and on TouhouOS under the Linux personality and the outputs (results, `errno` values, edge cases) must be identical. The tests are the specification.

## What a Linux program asks of a kernel (measured)

`tools/linuxcensus.c` is a small `ptrace` counter we wrote (no `strace` is needed) and `tools/linuxcensus.py` runs it over a set of programs inside WSL: `wsl.exe -e python3 tools/linuxcensus.py`. The first run (Ubuntu 24.04 in WSL, kernel 6.18) covered nine programs: `true`, `ls -l`, `cat`, a `sh` pipeline, Python doing nothing, Python with threads, sockets and hashing, a `gcc -c`, a static glibc hello, and a hello that makes raw system calls without any libc.

* **60 different system calls in all.** A program with no libc needs **3** (`execve`, `write`, `exit_group`); a static glibc hello needs **17**; `ls`, `cat` and a shell need about 40; Python and gcc need a few more (`clone3`, `epoll_create1`, `sockets`, `vfork`, `wait4`, `pipe2`, `getrusage`).
* The ten calls **every** program makes before its first line of code: `execve`, `brk`, `arch_prctl(ARCH_SET_FS)`, `set_tid_address`, `set_robust_list`, `rseq`, `prlimit64`, `mprotect`, `fstat`, `exit_group`; then `openat`, `mmap`, `read`, `pread64`, `close`, `access` for the dynamic loader.
* The flag values that matter: `mmap` is `PRIVATE|FIXED|DENYWRITE` (the loader mapping libraries), `PRIVATE|ANONYMOUS`, `SHARED`; `clone` with `CHILD_CLEARTID|CHILD_SETTID` (fork-like) and `clone3` for threads; `futex` `WAKE|PRIVATE` and `WAIT_BITSET`; `ioctl` `TCGETS` only. `rseq` and `set_robust_list` can be refused (glibc copes); `lgetxattr`/`listxattr` can answer "not supported".
* The full table is `build/linuxcensus.md` after a run.

## Where TouhouOS stands (read from the code, 2026-11-03; the loader line was overtaken by L2 on 2026-11-08, see "State: L2")

* About 100 native system calls with **our own numbers and structures**. They stay: they are the native ABI (`shared/syscall.h`).
* The kernel's loader for *native* programs takes only **static, fixed-address ELF files** (`ET_EXEC`, `PT_LOAD`). A Linux program also gets `ET_DYN`, `PT_INTERP` and the auxiliary vector (`kernel/linux/loader.c`).
* Present and useful: `futex`, `mmap`/`mprotect`/`brk`, `fork`/`execve`/`waitpid`, pipes, ptys, sockets, `procfs`, signals (our own layout), per-thread FS base (`set_tls`), FXSAVE state per task (SSE2; no AVX: `OSXSAVE` is off, so a libc will pick its SSE2 paths), a 47-bit user address space.
* Missing for Linux: the `*at` family and `dirfd` paths, `clone` with Linux's flag semantics (thread groups, `SETTLS`, `CHILD_CLEARTID` with the futex wake), `vfork`, Linux's signal ABI (`rt_sigaction`, `sigaltstack`, `siginfo` and `ucontext` frames, restorers), `epoll`/`eventfd`/`timerfd`/`signalfd`, the `getdents64`, `stat`, `statx` layouts, `set_tid_address`, `arch_prctl`, `prlimit64`, `madvise`, a Linux-shaped `/proc/self`, and 32-bit compatibility mode (there is no 32-bit user segment).

## The design

* **A personality per process.** The `syscall` entry looks at a per-process ABI flag: *native* (today's table) or *Linux* (a second table keyed by `rax`, written from the man pages). The flag is chosen at `execve` (a launcher, `linux PROGRAM`, like a user-mode emulator's front end, and later rules by what the file asks for, e.g. an interpreter path in the Linux root) and inherited by `fork`. Native programs are untouched.
* **A Linux root directory** (`/linux` or a volume) holds a user-provided distribution tree; paths a Linux process names are resolved inside it (chroot-like), `/proc` and `/dev` are Linux-shaped views.
* **The loader grows** `PT_INTERP`, `ET_DYN`, `PT_TLS` and a correct initial stack with the auxiliary vector (`AT_PHDR`, `AT_PHENT`, `AT_PHNUM`, `AT_PAGESZ`, `AT_BASE`, `AT_ENTRY`, `AT_RANDOM`, `AT_SECURE`, `AT_HWCAP`, `AT_EXECFN`, `AT_PLATFORM`; a vDSO is optional: glibc and musl fall back to real calls without one).
* **Our own dynamic linker** is a separate, later question for *our* programs (they are static today); Linux programs bring theirs.

## State: what runs now (L0 and L1, 2026-11-03)

`linux PROGRAM [ARGUMENT...]` runs a **static x86-64 Linux executable**: either a program with no C library at all (the kit in `user/linuxtest`) or one linked statically with glibc. `native PROGRAM` is the way back for a native tool started from inside a Linux program. Files and directories, signals (the real-time signals 32 to 64 with queued `siginfo` that says who sent each signal, handlers with `siginfo`, the alternate stack, the floating-point state, `SA_RESTART`), threads (`clone` with `CLONE_THREAD`, futexes, thread-local storage, `pthread_cancel`, the C library's set-id broadcast) and timers (`alarm`, `setitimer`, POSIX timers, the CPU-time clocks, `clock_nanosleep`) work too, and so does `waitid`; sockets, `poll`, `epoll`, `eventfd` and `timerfd` are there too (see "Sockets, poll and event descriptors" below); `signalfd` is not (see "Next" below). Dynamically linked programs are "State: L2" below.

**On real hardware.** The six glibc test programs were copied to the Dell OptiPlex (Core i5-7500, Kaby Lake) on 2026-11-04 and run there under the Linux personality: all six print exactly what a real Linux prints, the signal and thread programs included (real CPUID and FXSAVE state, real timers).

**How it is built**

* **The personality.** `Process.abi` is `ABI_NATIVE` or `ABI_LINUX`. `syscall_dispatch` (`kernel/sys/syscalls.c`) sends a Linux process's calls to `linux_syscall`; everything else is as before. `fork` copies the personality, `execve` keeps it unless the new native call `setabi` (119, used by `linux` and `native`) asked for the other one for that one exec.
* **The table** (`kernel/linux/syscall.c`, numbers in `numbers.h`). Native errno values, open and mmap flags, signal numbers up to 31 and the argument registers are already Linux's, so a call that means exactly what a native call means is routed to the native handler (`NATIVE(...)`); the rest have handlers of their own (`OWN(...)`): `arch_prctl`, `set_tid_address`, `prlimit64`/`getrlimit`, `uname`, `newfstatat`/`stat`/`fstat` with Linux's 144-byte struct, `readlinkat`, `readv`/`writev`, `poll`, `clock_gettime`, the `*at` calls (`openat`, `mkdirat`, `unlinkat`, `renameat`, `faccessat` ...), `pread64`/`pwrite64`, `clone` (the fork forms), `pipe2`, `dup3`, `time`, `gettimeofday`. A call with no entry answers `ENOSYS` and is named once in the kernel log (tag `Outside World`); `linux.trace` on the kernel command line logs every call with its result.
* **Signals, threads, timers.** `kernel/linux/signal.c` has `rt_sigaction`, `rt_sigprocmask`, `rt_sigpending`, `rt_sigsuspend`, `rt_sigtimedwait`, `sigaltstack` and `rt_sigreturn`, and builds the handler's frame as x86-64 Linux does (`struct rt_sigframe`: the restorer as return address, a `ucontext` with the registers, a `siginfo`, the FXSAVE state below); `kernel/linux/sigsend.c` has `kill`, `tkill`, `tgkill`, `rt_sigqueueinfo`, `rt_tgsigqueueinfo` and `waitid`; `kernel/linux/timers.c` has `setitimer`, `getitimer`, the POSIX timers, `clock_gettime`, `clock_getres`, `nanosleep`, `clock_nanosleep`, `times` and `getrusage`; `kernel/linux/ids.c` has `setreuid`, `setregid`, `setresuid`, `getresuid`, `setresgid` and `getresgid`, which the C library's `seteuid` and its set-id broadcast (signal 33, sent to every thread so that each makes the call itself) are built on. The credentials belong to the process here, so the broadcast finds the work done, and there is no saved set-user-ID: it reads as the effective id and is not checked. A fault in a Linux program runs its SIGSEGV handler instead of always killing it. `clone` with `CLONE_THREAD` creates a native thread (`task_create_thread`); `futex` (wait, wake, requeue, the bitset forms, private and clock flags, absolute timeouts) is a wrapper over the native futex queues.
* **How the real-time signals are represented.** The kernel's signal sets are `u64` (`kernel/include/siginfo.h`): signal *n* is bit *n*, exactly the bit the native 32-bit masks always used, so everything written for the 31 native signals with `1U << sig` still means what it did and the native ABI (`shared/abi.h`, libgap) did not change; signal 64, which would need a 65th bit, is carried by bit 0, which no signal uses (`sigbit()`, `sig_first()` put it last). Linux's own order (bit *n*-1 for signal *n*) is one rotation away and `kernel/linux/signal.c` converts at the system call boundary. The dispositions are `sigact[65]`. Native processes know signals 1 to 31 (`NSIG`) and never see anything else. Behind each pending set (one per thread, one per process) a process of the Linux personality keeps a queue of entries, each a signal number and its 128-byte `siginfo`, from a fixed pool of 1024 (at most 128 per process; `kernel/sys/signal.c` explains the invariants): a standard signal is held once, with the `siginfo` of its first sender, as on Linux; a real-time signal queues as often as it was sent, lowest number first and oldest first among equals, and `sigqueue` fails with `EAGAIN` when there is no room. `kill(2)` of a real-time signal queues too. Native processes have no entries, only bits, and the cost of a native `kill`, `tgkill`, `sigaction` or `sigprocmask` did not change by more than 4 %: `user/test/sigbench` run in QEMU with `-icount shift=0` (one guest instruction is one nanosecond, so the numbers do not depend on how busy the PC is; the wall clock of a loaded PC moves them by 15 % or more) with the same initrd under the kernel before and after reads 1532 and 1584 for a `kill` with its handler, 1687 and 1728 for `raise`, 299 and 289 for a `sigaction`, 161 and 151 for a system call that does nothing (`signal_deliver` got a short path for the common case of nothing to deliver). Signals that are deliverable together get their frames stacked on top of each other, as Linux does, so the handler of the highest number runs first. `siginfo` says who sent the signal: `kill` is `SI_USER` with the sender's pid and real user id, `tkill`/`tgkill`/`raise`/`pthread_kill` `SI_TKILL`, `sigqueue` `SI_QUEUE` with the caller's value (the caller's own `siginfo` is passed on word for word, but may not claim to be `kill` or the kernel unless it signals itself), a terminal's `^C`, `alarm` and the interval timers `SI_KERNEL`, a broken pipe `SI_USER` from the process itself, a POSIX timer `SI_TIMER` with its id, value and overrun count, `SIGCHLD` `CLD_EXITED`, `CLD_KILLED`, `CLD_STOPPED` or `CLD_CONTINUED` with `si_pid`, `si_uid`, `si_status` and the child's CPU time. The C library's `pthread_cancel` (signal 32) and set-id broadcast (signal 33) ignore every signal that is not an `SI_TKILL` from their own process; that is why this had to be exact.
* **Timers and clocks.** The system tick is 1 ms; every expiry is rounded up to a tick and the clocks count whole milliseconds. `alarm` and `setitimer(ITIMER_REAL)` are one timer (`Process.alarm_at` and `alarm_interval`, checked by `alarm_tick`). `ITIMER_VIRTUAL` and `ITIMER_PROF` count the ticks the scheduler charges to the process, a tick going to whatever was running when it arrived and to user time when it interrupted user mode (`Task.utime_ticks`, set in `task_on_trap_return`): samples, as the CPU times of a classic Unix were. POSIX timers (`timer_create` with `SIGEV_SIGNAL`, `SIGEV_NONE`, `SIGEV_THREAD_ID`, so also the C library's `SIGEV_THREAD`, which runs on a helper thread and signal 32) sit in a list that the tick looks at while any is armed; while the signal of a timer waits, further expirations only count as an overrun (`si_overrun`, `timer_getoverrun`); timers are dropped by `execve` and at exit. `clock_gettime` knows `CLOCK_REALTIME`, `MONOTONIC`, `PROCESS_CPUTIME_ID`, `THREAD_CPUTIME_ID`, `MONOTONIC_RAW`, the coarse clocks, `BOOTTIME` and `TAI`; the CPU clocks are the same sampled ticks; `clock_getres` says 1 ms for all of them.
* **The initial stack** (`kernel/linux/stack.c`): argc, argv, envp and the auxiliary vector as the psABI describes them (`AT_PHDR`, `AT_PHENT`, `AT_PHNUM`, `AT_PAGESZ`, `AT_BASE`, `AT_ENTRY`, the user ids, `AT_PLATFORM`, `AT_HWCAP`, `AT_CLKTCK`, `AT_SECURE`, `AT_RANDOM`, `AT_HWCAP2`, `AT_EXECFN`), 16-byte aligned. The ELF loader reports where the program headers ended up.
* **How it is checked.** The facts in the code (call numbers, constants, struct layouts) are compared with a real Linux by `tests/host/test_linux_abi.py`. The behaviour is compared by running the same program on a real Linux (`tools/linux-oracle.py`, in WSL) and on TouhouOS (`tests/case_linux.py`) and diffing the output line by line: the freestanding programs in `user/linuxtest` (a 90-line probe that makes many calls on purpose wrong, the stack and auxv checker, exec) and ordinary C programs in `tests/linux/src` linked statically with glibc, which the test downloads into the guest from a host HTTP server (they are build products in `build/linux-inputs`, never committed, never part of an image). The stored outputs are in `tests/linux/golden`. The signal, timer and cancellation programs (`glibc_rtsig`, `glibc_siginfo`, `glibc_timers`, `glibc_cancel`, `glibc_setxid`) are run by `tests/case_linux_signals.py` (prefix `linux_rt_`; `LINUX_ONLY=glibc_timers` runs one of them, `LINUX_TRACE=1` logs every call), and the layouts and numbers they rely on are checked by `tests/host/test_linux_signals_abi.py`. `ORACLE_ONLY=NAME` limits `tools/linux-oracle.py` to some programs.
* **Adding a call.** Add its number to `numbers.h` (the host test then checks it against the headers of the real system), route it to a native handler or write one, add a line to a probe or a corpus program that exercises it and its errors, regenerate the stored output with `wsl.exe -e python3 tools/linux-oracle.py`, and make the guest print the same. When a program asks for something that is missing, `dmesg | grep "Outside World"` names it.

**Approximations to know about** (each is a place where behaviour differs from Linux on purpose, for now)

* A `clone` with `CLONE_VM` (posix_spawn, `system()`) gives the child a *copy* of the address space, not a shared one: the exec that follows works, but a program that passes data back through shared memory before the exec does not. `clone3` answers `ENOSYS`, which makes the C library fall back to `clone`.
* `prlimit64`/`setrlimit` report this system's limits (an 8 MiB stack, 64 descriptors) and accept new values without enforcing them. `uname` reports a Linux release string (`6.1.0-gensokyo`) so that programs that check the kernel version are satisfied. The coarse, raw, boot-time and TAI clocks are the ordinary ones.
* `exit` ends the calling thread, and the last thread out ends the process. `vfork` is `fork`. `fsync`, `flock` and `madvise` do nothing. The environment and arguments of a program are limited to 32 KiB together.
* Signals: signal 31 is `SIGSYS` for a Linux program, an ordinary signal that it can catch, block, send, wait for and get from a POSIX timer (freed on 2026-11-09 at the owner's word; the test `linux_sigsys_is_an_ordinary_signal` compares `tests/linux/src/glibc_sigsys.c` with a real Linux). Until then it was hidden, because the native thread library uses signal 31 as its `SIGCANCEL`, a sticky thread-directed request that never runs a handler; that meaning is now the native personality's alone (`cancel_bit()` in `kernel/sys/signal.c`: for a Linux task the bit is an ordinary one). A Linux program cannot cancel a native thread with it: `tgkill` and `tkill` at a native thread answer `EINVAL`, and a `kill` of a native process with 31 is dropped. A native program cannot send it to a Linux one either (`kill` answers `EINVAL` for 31 in the native personality); a process that changes personality at `execve` loses signal 31 from its mask, since the two meanings must not be carried over. The default action of a signal that dumps core on Linux (`SIGSEGV`, `SIGABRT`, ...) ends the process as "killed by the signal" (`CLD_KILLED`, never `CLD_DUMPED`; there are no core files). A signal whose action is "ignore" is thrown away when it is sent unless some thread blocks it or waits for it. `SA_NOCLDWAIT`, and a `SIGCHLD` that is ignored reaping its children by itself, are not implemented. `execve` discards the pending signals (POSIX keeps them). `kill(pid)` takes the id of a process, not of a thread. At most 128 signals queue per process (the pool holds 1024 for the whole system); beyond that `sigqueue` fails with `EAGAIN` and a standard signal arrives without a `siginfo`. When signals are deliverable together their frames are stacked in the order Linux uses; the thread that takes a process-directed signal is whichever passes through the delivery code first (a thread that waits for it in `sigtimedwait` is preferred). Only `read`, `write`, `readv`, `writev`, `pread64`, `pwrite64`, `wait4`, `waitid`, `open` and `openat` are restarted after an `SA_RESTART` handler. `waitid` does not accept `P_PIDFD`; `wait4` and `waitid` store zeros in the `rusage` they are given (the resource usage of a child is not kept).
* Timers: the tick is 1 ms, so every time is rounded up to a millisecond and `clock_getres` says 1 ms (Linux says 1 ns for most clocks); `ITIMER_VIRTUAL`, `ITIMER_PROF` and the CPU-time clocks are sampled by the tick. POSIX timers on the CPU-time clocks (`timer_create(CLOCK_PROCESS_CPUTIME_ID)`), the per-thread and per-process clock ids of `pthread_getcpuclockid` and `clock_nanosleep` on a CPU clock answer `EINVAL` (Linux accepts them). A `CLOCK_REALTIME` timer armed with an absolute time does not follow later steps of the wall clock. A timer signal that is still waiting when its timer is re-armed or stopped is delivered anyway (the kernel of the oracle, 6.18, takes it back and older ones deliver it, as this system does). `times` and `getrusage` report the same sampled CPU ticks, with the children the process has waited for (`Process.child_ticks`); the other fields of `struct rusage` (memory, faults, context switches) are zero, and `wait4` does not give the child's usage.

**Next, in this order** (as written on 2026-11-03; 1 and 2 are done, see "State: L2"; 3 is done too, see the signals paragraphs above): (1) dynamically linked executables (`ET_DYN`, `PT_INTERP`, the interpreter's load address in `AT_BASE`, file-backed `mmap` with the flags and offsets a dynamic linker uses), which also needs (2) a Linux root directory (`/linux`) that the paths of a Linux process are resolved in, with Linux-shaped `/proc/self` and `/dev`; (3) (done, 2026-11-08: the real-time signals, who-sent-it in `siginfo`, `setitimer` and POSIX timers, `waitid`; `signalfd` is left for after the sockets, because it is a descriptor that `epoll` has to watch); (4) (done, 2026-11-08: sockets, `poll`, `epoll`, `eventfd`, `timerfd`, see "Sockets, poll and event descriptors" below; `signalfd` is left: it is a descriptor `epoll` can already watch, see "The readiness interface"); (5) choosing the personality at `execve` by itself (a native ELF note in our own programs, `PT_INTERP` and `.note.ABI-tag` in theirs) so that a Linux program can be started from the shell by name; (6) then the checkpoint after that, L3: the census programs themselves (`ls`, `cat`, `sh`, Python, `gcc -c`) from a user-provided root.

## State: L2, dynamically linked programs and the Linux root (2026-11-08)

`linux /bin/ls`, `linux /bin/sh -c 'echo $((1+2))'`, `linux /bin/bash script.sh` run the programs of a Ubuntu 24.04 (glibc 2.39) unchanged, from a root directory that the user provides, and print what a real Linux prints. Nothing of that Linux is in the repository, an image or the public export: the archive is built under `build/` from the WSL Ubuntu of the development PC and is third-party data like any test input.

**How to get a Linux root onto a machine**

1. On the development PC: `python tools/make-linux-root.py` writes `build/linux-inputs/linux-root.tar` (about 15 MB: `ld.so`, glibc and the libraries the programs need as `ldd` reports them, bash, dash as `/bin/sh`, forty-odd coreutils and friends, the usr-merge symlinks, `/etc/passwd`, `/etc/group`, `/etc/nsswitch.conf`, `/etc/os-release`, `/etc/hosts`, empty mount points; the list is a table at the top of the script). `--gzip` makes `linux-root.tar.gz` (a third of the size), `--programs` limits it. The script runs itself inside WSL on Windows.
2. Copy the archive to the machine, for example to `/HumanVillage/linux-root.tar` (the lead does this for the Dell), or fetch it over the network.
3. As root: `linuxroot /HumanVillage/linux-root.tar`. It makes `/linux`, mounts a tmpfs on it, and unpacks the archive with the `tar` applet (modes, owners, times and symbolic links are kept; a device node or a pipe in the archive is skipped with a line; a hard link comes out as a copy; a plain tar or a gzip one). It then replaces `/linux/etc/resolv.conf` by the machine's own. Unpacking the 15 MB archive takes about a second in QEMU and the tree occupies about 15 MB of RAM (tmpfs pages, shown as `Tmpfs` in `/proc/meminfo`); a root with more programs costs what its files weigh. `linuxroot` alone says whether a root is mounted, `linuxroot -d` empties it and unmounts it (the memory comes back; a Linux program that still runs in it keeps the mount, empty).
4. Any user: `linux /bin/ls /`. Everything the program does with a path is read in the tree under `/linux`.

**The Linux root: what a Linux program sees**

* `Process.root` is the top of the tree (a vnode reference; NULL for a native program). `resolve()` in `kernel/fs/vfs.c` starts an absolute path there for every lookup that a process makes with its credentials (open, stat, mkdir, exec, the socket paths ...); the kernel's own lookups (credentials NULL: the boot code, the mount policy, DHCP writing `/etc/resolv.conf`) always start in the real root. `fork` copies the root, `execve` of a Linux program keeps it, a native `execve` drops it. The decision and the rules are in `kernel/linux/root.c`.
* Inside the tree `..` at the top is the top, an absolute symbolic link is read from the top (a link in `/lib64` that names `/lib/x86_64-linux-gnu/ld-linux-x86-64.so.2` finds the file inside the root, not the native `/lib`), and **`/proc`, `/dev`, `/tmp`, `/sys` and `/run` are the machine's own** (the lookup of exactly these five names at the top goes to the real root; `/run`, which the machine does not have, falls back to the tree's own empty directory). `/tmp` is the machine's `/tmp` (`/BambooForest`): it is how native programs and Linux programs hand each other files, and where the tests put their programs. Going up out of one of these directories (`/tmp/..`, `/dev/..`) lands in the top of the tree again. There are no bind mounts in this VFS; the rule is five names in `resolve()`.
* The native directories (`/HumanVillage`, `/Hakurei`, `/ScarletDevilMansion`, `/BambooForest`, `/YoukaiMountain`) and `/linux` itself do not exist in the tree: a Linux program cannot see or reach them, except through the five names.
* The working directory: a program entering the root keeps its directory when the directory is visible under the same path (`/tmp/x` is, `/HumanVillage/reimu` is not) and otherwise starts in `/`. `getcwd` and `/proc/self/cwd` give the Linux path.
* `linux -r PROGRAM` (`setabi(ABI_LINUX | ABI_NOROOT)`) runs the program in the real root, which is where the static test programs of L0 and L1 live (`/ScarletDevilMansion/share/linux-tests`). Without anything mounted on `/linux` every path is a real one, so the earlier tests did not change. A Linux program that runs a native one (`native PROGRAM`, see the limit below) resolves it in the real root.
* `/proc/self/maps` (`start-end perms offset dev inode  name` as Linux prints it, with `[heap]` and `[stack]`; no library names, because a mapping does not remember its file), `/proc/self/fd/N` and `/proc/self/exe` (the path the program was started by, not resolved), `/dev/null`, `zero`, `urandom`, `tty`, `console`, `pts/N`, and the links `/dev/stdin`, `stdout`, `stderr` and `fd` (new in the native `/dev`) are the machine's.

**The loader** (`kernel/linux/loader.c`, `elf_read_headers`/`elf_map` in `kernel/sys/exec.c`; written from the ELF specification and the psABI)

* An `ET_EXEC` is mapped where it says. An `ET_DYN` (a PIE, a static-PIE) goes to `0x555555554000` (the address Linux uses without randomization), aligned to its strictest segment. If the file has `PT_INTERP`, that file is opened in the new root (a missing interpreter is `ENOENT`, as `execve(2)` says) and mapped as well, at an address from the mmap area; the process starts at the interpreter's entry point. The break starts after the program, not after the interpreter.
* The auxiliary vector: `AT_PHDR`, `AT_PHENT`, `AT_PHNUM` of the program, `AT_BASE` the interpreter's load address (0 without one), `AT_ENTRY` the program's entry point, `AT_PAGESZ`, `AT_CLKTCK`, `AT_PLATFORM`, `AT_HWCAP`, `AT_HWCAP2`, `AT_SECURE`, `AT_RANDOM`, `AT_EXECFN`, `AT_MINSIGSTKSZ`, the user ids. There is no vDSO (`AT_SYSINFO_EHDR` is absent): `clock_gettime`, `gettimeofday` and `time` are real calls; `dl_iterate_phdr` lacks the `linux-vdso.so.1` entry.
* `#!` scripts are looked up in the new root as well (`/bin/sh` of the tree).
* The tree has no `/etc/ld.so.cache`: `ld.so` tries the system directories (`/lib/x86_64-linux-gnu`, `/usr/lib/x86_64-linux-gnu`, `/lib`, `/usr/lib` and the `glibc-hwcaps` and `tls` subdirectories) one by one, about forty failed `openat` calls per library; it is only a little slower. `LD_LIBRARY_PATH`, `LD_DEBUG`, `dlopen` and `dlmopen` need nothing from the kernel beyond what is below.

**Memory mapping** (`do_mmap` and friends in `kernel/sys/syscalls.c`, `kernel/sys/uvm.c`, `kernel/linux/mem.c`; the VM is the native one, with these changes outside `kernel/linux`)

A private file mapping is filled when it is made: the pages are allocated and read from the file at the offset, so `libc.so.6` costs 2 MB per process that maps it, and there is no page cache to share. What a dynamic linker needs works: a mapping at an offset, `MAP_FIXED` over a `PROT_NONE` reservation (the old pages go first, and a bad file descriptor or offset is refused before anything is replaced), partial `munmap` (the tail or the middle split the mapping), `mprotect` of any part (RELRO, the guard gaps; a `PROT_NONE` page that is already in use is no longer reachable from user mode, but a system call can still read it), `MAP_DENYWRITE`, `MAP_NORESERVE`, `MAP_POPULATE` and `MAP_STACK` accepted, an unaligned offset is `EINVAL`, a write-only descriptor for a private mapping is `EACCES`. `madvise(MADV_DONTNEED)` and `MADV_FREE` give back the pages of private memory that was not read from a file (the next access finds zeros: the heap recycling of a C library relies on it); the other advice is accepted and ignored. `mremap` shrinks, grows in place when the pages after are free and otherwise moves with `MREMAP_MAYMOVE`, taking the pages along without copying (`MREMAP_FIXED` and `DONTUNMAP` are `EINVAL`). `tests/linux/src/map_tour.c` (`linux_dyn_mmap_tour`) pins all of this against a real Linux.

**Calls added or changed for L2** (`kernel/linux/fsops.c`, `mem.c`, the table block "L2" in `syscall.c`): `statfs`, `fstatfs` (Linux's 120-byte structure), `fchdir`, `fchmod`, `fchown`, `lchown`, `fchmodat`, `fchownat`, `utimensat` (also as `futimens`), `linkat`, the extended-attribute calls (all "not supported": `ls`, `cp` and `mv` ask and carry on), `fadvise64` and `msync` (hints), `getpgrp`, `getsid`, `getgroups`, `madvise`, `mremap`, and `fcntl` with `F_DUPFD_CLOEXEC` and the advisory locks (they always succeed). `select`, `pselect6` and `ppoll` (now `kernel/linux/epoll.c`, on the readiness interface of the next section): a shell's line editor asks `pselect6` whether a key is waiting and takes "not implemented" for the end of its input (found by typing to an interactive bash); the console has no wait queue, so it is looked at every 2 ms, and the signal mask of the p-variants is honoured. `ioctl` has a handler of its own (`kernel/linux/ioctl.c`): the terminal attributes (`TCGETS`, `TCSETS`, `TCSETSW`, `TCSETSF`) are translated between Linux's 36-byte `struct termios` (its bit values and control character positions) and the native `struct gtermios`, so that readline, `stty` and the like read and set the right things; what Linux has and the native terminal does not (`IXON`, `ECHOCTL`, `IEXTEN`, the characters for `^R ^W ^V ^O`) is made up as a default console has it and ignored when it is set; every other request goes to the native handler (the window size and process group requests are the same numbers and layouts). `open` is `openat(AT_FDCWD, ...)`. Native handlers changed: `setabi` takes `ABI_NOROOT`; `mmap` checks before it replaces; `chdir` and `fchdir` share `process_set_cwd`. Answered `ENOSYS` without a log line: `mincore`, `copy_file_range` (`cp` falls back to read and write). (`socket` and the rest of the network, `epoll`, `getrusage` and `times` were `ENOSYS` when this was written; the first two have come since, see the next section, and the others with the signals work. `ls -l` and `id` try the name service cache's socket once and carry on: it is a UNIX socket path that does not exist, `ENOENT`.)

**Measured** (QEMU with TCG on the development PC, shared with other guests, so read them as orders of magnitude): `linux /bin/ls /` from the command to its output takes 0.2 to 0.4 s including the round trip through the shell (a dash script of sixty-odd processes takes ten seconds, so about 150 ms per dynamic process, most of it `ld.so` mapping and relocating `libc.so.6`: a private file mapping is copied when it is made); `linuxroot` of the 15 MB archive takes 1.0 to 1.4 s and the tree holds 14.7 MB of RAM (`Tmpfs` in `/proc/meminfo` went from 39.9 to 54.6 MB). The native `fork` + `exec` + `wait` of `/bin/true` (300 in a loop, three loops, two rounds each) took 23 to 29 ms before and 25 to 29 ms after the branch, within the noise of the shared host: `resolve()` reads `current->proc->root` once, the commit of an exec checks one pointer.

**How it is checked** (`python tools/qemu-slot.py -- python tests/run_all.py linux_dyn`; every test needs WSL for the programs and the root and says `SKIP` without it)

* `linux_dyn_static_pie`, `linux_dyn_loader` (dynamic PIE, non-PIE with an interpreter, `dlopen` through `LD_LIBRARY_PATH` and from the system directories with constructors, destructors and thread-local storage in a library, `fork` + `exec` and `posix_spawn` of another dynamic program, `system()`, `popen()`), `linux_dyn_ld_debug_shape`: the output of `tests/linux/src/dyn_*.c` equals the stored output of a real Linux (`tests/linux/golden`, made by `wsl.exe -e python3 tools/linux-oracle.py`).
* `linux_dyn_glibc_corpus` and `linux_dyn_signals_and_threads`: the L1 corpus (`glibc_libc.c`, `glibc_dir.c`, `glibc_sys.c`, `glibc_signals.c`, `glibc_threads.c`) built as dynamically linked PIEs gives the same output as the static ones.
* `linux_dyn_shell_and_tools`: three scripts (`tests/linux/scripts`: files and directories; pipelines and the shell language; the environment, `/proc/self/fd`, `/dev` and the paths of the root) run by dash and by bash in a fresh directory print what the same script prints on a real Linux; `ls`, `cat /etc/os-release` and `sh -c 'echo $((1+2))'` run; a user without privileges (`su reimu -c 'linux /usr/bin/id'`) runs Linux programs and cannot write root's files.
* `linux_dyn_interactive_bash`: an interactive bash typed to over the console (readline sets the terminal through the translated `termios`, echoes once, edits a line with a backspace, runs a command).

**Approximations to know about** (each is a place where behaviour differs from Linux on purpose, for now)

* The tree is RAM: the whole root is unpacked into a tmpfs when it is first wanted, and a tmpfs may use at most half of the machine's RAM together with everything else in it. Hard links in an archive come out as copies.
* `/proc/self/fd/N` and `/dev/fd/N`, `/dev/stdout` and the like are symbolic links to the *path* the descriptor was opened by (a pipe shows as `pipe:[N]`, which is not a path), so reading the link works but opening the name would not. A Linux program's `open()` of these names is therefore answered by the Linux personality itself (`lnx_open_via_proc`): it hands out a new descriptor for the open file, whatever it is, which works for pipes, terminals and files whose name is gone (`echo > /dev/stdout`, bash's `<(command)`). The new descriptor shares the file position with the old one, where a real Linux makes a new open file for a regular file. Native programs do not get this, and a name reached some other way (`cd /proc/self/fd; cat 1`) is the plain symbolic link.
* `posix_spawn` and `system()` use `clone(CLONE_VM | CLONE_VFORK)`: the child gets a copy of the address space and the parent is not suspended, so a spawn that fails at `execve` still returns 0 and the child exits with status 127 (a real Linux returns `ENOENT`, because parent and child share the memory where the error is stored).
* No vDSO, no `ld.so.cache`; `AT_HWCAP` is the CPUID feature word and `AT_HWCAP2` is 0; the program is always loaded at the same address (no randomization). A page that is `PROT_NONE` and already resident can still be read by a system call that is handed its address (a store from user mode faults).
* `uname` says `Linux gensokyo 6.1.0-gensokyo`; `/proc/self/stat` and `/proc/<pid>/status` have this system's format, not Linux's, so `ps`, `top`, `pidof` and the like from a Linux distribution do not work yet; `/proc/self/maps` has no file names.
* `native PROGRAM` from inside a Linux program does not work: a native binary exec'd by a Linux process keeps the Linux personality (it must be chosen by the kernel from the file, the old "next" item 5).

## Sockets, poll and event descriptors (2026-11-08)

Event loops, servers, clients and Python sit on sockets, `poll`, `epoll`, `eventfd`, `timerfd` and `pipe2`. The native system had BSD-style sockets (AF_UNIX stream, AF_INET stream and datagram, `kernel/fs/socket.c`, `kernel/net/`), `poll` and `pipe`; the Linux table answered none of the calls around them. The native sockets already use Linux's errno values, option and flag numbers and `sockaddr_in`, which decides most of the table: a call that means the same thing goes straight to the native handler, the others have a handler of their own in `kernel/linux/net.c` (sockets) or `kernel/linux/epoll.c` (waiting for events). The constants and structures are in `kernel/linux/netabi.h` and are compared with the C library's by `tests/host/test_linux_net_abi.py`; the behaviour is compared with a real Linux by the programs `tests/linux/src/net_*.c` (`tests/case_linux_net.py`, golden files from `tools/linux-oracle.py`): a TCP echo with a server thread and a 1 MB transfer, a non-blocking connect completed by `poll`, UDP, AF_UNIX streams and datagrams with descriptors in messages, `shutdown` and end of file, `SO_ERROR` after a refused connect, `EADDRINUSE`, `ECONNREFUSED`, `EPIPE` with and without `MSG_NOSIGNAL`, `EAGAIN`, an `epoll` loop that serves ten clients with edge-triggered reads, `eventfd` wake-ups between threads, a `timerfd` that ticks, and one program that talks to Python servers on the host through QEMU's user networking (`10.0.2.2`).

### The readiness interface

`poll`, `select` and `epoll` all ask the same two questions of a file, and a file type answers them with two members of its `FileOps` (a device node: of its `VNodeOps`); `kernel/include/pollq.h` has the contract:

* `int poll(File *f)`: the bits of `POLLIN`, `POLLOUT`, `POLLERR`, `POLLHUP`, `POLLPRI`, `POLLRDHUP` that hold right now. It may sleep (the network lock).
* `WaitQueue *pollwq(File *f)`: the queue the file wakes (`wq_wake_all`/`wq_wake_one`) whenever the answer of `poll` may have changed. A spurious wake-up is harmless, a missing one is a hang. The queue must live as long as the `File`. If the answer of `pollwq` can change (an unconnected socket that starts to listen) the old queue is woken once at that moment, and `poll`/`epoll` look at the queue again after every wake-up. Returning `NULL` says "I cannot tell you": a waiter then looks again every 2 ms, which is all the native `poll` ever did. Pipes, UNIX sockets (streams and datagrams), Internet sockets, `eventfd`, `timerfd` and `epoll` itself provide both; terminals, pseudo-terminals and the input devices provide `poll` only (so they are polled every 2 ms).

The mechanism is a hook in `wq_wake_one`/`wq_wake_all` (`kernel/sched/task.c`): a wait queue has a list of `PollWaiter`s, each with a callback that runs inside the wake-up (interrupts off, possibly in an interrupt handler, possibly under the network lock) and may only set a flag, link a node and wake a task. A file type therefore needs no new wake-up site: the wake-ups it already does for blocked readers and writers are what poll sees. `poll` and `select` attach one waiter per descriptor and sleep on one private queue (the order is: clear the flag, ask the files, sleep only if the flag is still clear); the native `poll` system call uses the same engine now and no longer spins. A future `signalfd` needs `poll` (readable while a signal of its set is pending) and a queue that the signal code wakes when it queues a signal; nothing else.

### epoll, eventfd, timerfd

* **epoll** (`kernel/fs/epoll.c`): registrations are keyed by (file, descriptor number) as on Linux, so a duplicate keeps a registration alive after the original descriptor is closed, and the registration vanishes when the last descriptor of the *file* is closed (`File.poll_watch`, `pollq_file_released` in `file_put`). Level-triggered, `EPOLLET`, `EPOLLONESHOT` (re-armed by `EPOLL_CTL_MOD`), `EPOLLIN/OUT/ERR/HUP/RDHUP/PRI`, user data, nested sets with the loop check (`ELOOP`) and a depth limit of 5, `EPOLL_CLOEXEC`. `EPOLLEXCLUSIVE` and `EPOLLWAKEUP` are accepted and ignored. Regular files and directories are `EPERM`. At most 512 events are returned by one call. A file without a wait queue is polled every 2 ms and its edge-triggered events are worked out by comparing with the last answer. `epoll_wait`, like `poll`, is never restarted after a signal handler.
* **eventfd** (`kernel/fs/eventfd.c`): counter and `EFD_SEMAPHORE`, `EFD_NONBLOCK`, `EFD_CLOEXEC`; the `EAGAIN`, `EINVAL` and blocking rules of `eventfd(2)` including the largest value `0xfffffffffffffffe`.
* **timerfd** (`kernel/fs/timerfd.c`): `CLOCK_MONOTONIC`, `CLOCK_BOOTTIME` (the same) and `CLOCK_REALTIME`; relative and absolute (`TFD_TIMER_ABSTIME`) deadlines, intervals, expiration counts, the old setting handed back by `timerfd_settime`. The resolution is a millisecond (the kernel clock's); a `CLOCK_REALTIME` deadline is converted to uptime when it is set, so a later step of the wall clock does not move it; `TFD_TIMER_CANCEL_ON_SET` is accepted and does nothing; `CLOCK_REALTIME_ALARM` and `CLOCK_BOOTTIME_ALARM` are `EINVAL`. A small kernel thread (started with the first timerfd, asleep while no timer is armed) wakes pollers when a timer goes off.

### UNIX-domain sockets

Streams and datagrams, names in tmpfs directories (`/tmp`, `/BambooForest`, `/dev`) or in the abstract namespace, `getsockname`/`getpeername` with the lengths Linux reports (2 for a socket without a name), `SO_PEERCRED` (and `SO_PASSCRED` with `SCM_CREDENTIALS`), descriptor passing, `MSG_PEEK`, `MSG_DONTWAIT`, `MSG_WAITALL`, `MSG_TRUNC`, `MSG_NOSIGNAL`, `SHUT_RD`/`SHUT_WR`. A datagram socket holds up to 256 KiB of messages; a datagram may be up to 130000 bytes; `connect` on a datagram socket sets the default destination (`AF_UNSPEC` undoes it). Descriptors in flight when the receiver closes are closed with it. A socket file can be made only in a tmpfs directory (`/tmp`, `/BambooForest`, `/dev`), not on a FAT or NTFS volume (`ENOTSUP`); a stream listener keeps at most 32 pending connections. The rules of unix(7) for an address (the length decides where the name ends, the family is checked, a name that starts with a NUL byte is abstract) are for Linux programs only: a native program's `bind` and `connect` read the path at the end of the family field up to its NUL and ignore the length, as they always did (the system call fuzzer passes lengths of a few bytes with a full path, and a name cut short would leave socket files in `/tmp`). Not there: `SOCK_SEQPACKET`, autobind of an unbound socket, `SO_PEEK_OFF`, `SCM_SECURITY`, and the per-socket receive timeouts (`SO_RCVTIMEO` is accepted and ignored on these sockets).

**Options that are accepted and do nothing** (a program that sets them and reads them back gets what it set, except where noted). TCP: `SO_SNDBUF`, `SO_RCVBUF` (the rings have a fixed size of 128 KiB; a read-back gives that size, not Linux's doubled value), `SO_LINGER` (kept and read back, but a close never waits or resets because of it), `TCP_KEEPIDLE`, `TCP_KEEPINTVL`, `TCP_KEEPCNT` (kept; no keep-alive probes are sent, `SO_KEEPALIVE` itself is only a flag), `TCP_CORK`, `TCP_QUICKACK`, `TCP_DEFER_ACCEPT`, `TCP_USER_TIMEOUT`, `TCP_SYNCNT`, `TCP_LINGER2`, `IP_MTU_DISCOVER`, `IP_RECVERR`, `SO_DONTROUTE`, `SO_OOBINLINE`, `SO_NO_CHECK`, `SO_PRIORITY`, `SO_PASSCRED`, `SO_RCVLOWAT`, `SO_SNDLOWAT`, `SO_TIMESTAMP`, `SO_SNDBUFFORCE`, `SO_RCVBUFFORCE`; `SO_REUSEPORT` is the same flag as `SO_REUSEADDR` (two listeners on one port are not load-balanced). UNIX-domain sockets: the sizes, `SO_LINGER`, `SO_PRIORITY`, the low-water marks and the timeouts; the on/off options (`SO_REUSEADDR`, `SO_KEEPALIVE`, `SO_PASSCRED`, ...) are kept so that `getsockopt` answers what was set. An option number the stack does not know is `ENOPROTOOPT`, as on Linux.

**Differences from Linux that the tests had to live with.** Loopback delivery is asynchronous here (the network thread moves a packet within a few milliseconds), where Linux hands it over before the sending call returns: a program that writes to one end of a loopback connection and polls the other once with a zero timeout may not see the data yet. `send` on a TCP socket that was never connected is `ENOTCONN` (Linux: `EPIPE`). A refused connect shows `POLLIN | POLLOUT | POLLERR | POLLHUP | POLLRDHUP` as Linux does. `connect` to a missing UNIX socket path is `ENOENT` for a Linux program (the native calls say `ECONNREFUSED`). A half-closed UNIX stream (`shutdown(SHUT_WR)` of the peer) reports `POLLIN | POLLRDHUP` and not `POLLHUP` to a Linux program, as `unix_poll` does; native programs keep the old answer. The descriptor table has 64 entries, so a server is limited to about 60 connections. The interrupted-call restarts of `SA_RESTART` (kernel/linux/signal.c) cover `read`, `write`, `wait4` and `open`, but not yet `accept`, `recvfrom`, `recvmsg`, `sendto` and `sendmsg`, which Linux restarts too; the C library of Python (PEP 475) and most event loops retry on `EINTR` themselves.

## Open questions

* Is the native ABI ever replaced by Linux's? (No for now: native stays ours, Linux is a translation.) A native `libgap` could later gain a dynamic linker of its own.
* The Linux root (decided by the owner on 2026-11-08, built the same day): a tar archive on the `HUMANVILLAGE` volume (FAT32 has no symbolic links, modes or hard links) that `linuxroot` unpacks into a tmpfs on `/linux` when it is first wanted. A volume with the tree unpacked (an ext4 or a UDF image) stays a possibility for a root too big for RAM.
* How much of `/proc` and `/sys` to fake, and how: decided by what the checkpoints need, not up front.
* Windows: see the next page when it exists. The shared pieces are the 32-bit compatibility mode, the loader work and the graphics path (software rendering; a GPU driver is its own project).
