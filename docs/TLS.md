# TLS and HTTPS: libtls

Most of today's internet is HTTPS only, so the system has a TLS client library, `libtls` (`user/lib/tls`, linked into every
program like the other libraries under `user/lib`), a Mozilla root certificate bundle (`/etc/ssl/certs/ca-bundle.pem`), and
`fetch` / `wget` that speak `https://`. Everything was written for this system, from the hash functions up; nothing was taken
from another library. The manual page is `man tls`; this file is the long version, including what is **not** done.

```
 fetch / wget  (user/bin/kappabox/net_fetch.c)                       URLs, redirects http<->https, -k, --cacert, -v
   |  tls.h: tls_ctx (trust anchors), tls_new / tls_handshake / tls_read / tls_write / tls_close, tls_info
   v
 tls.c       record layer (AEAD, sequence numbers, padding, alerts), handshake message plumbing, public API
 hello.c     ClientHello, ServerHello, HelloRetryRequest          hs13.c  TLS 1.3 key schedule and flight
 hs12.c      TLS 1.2 ECDHE client                                 x509.c asn1.c pem.c  certificates and the trust store
 sha2.c  chacha.c  aes.c  bn.c  x25519.c  ecc.c  rsa.c           the primitives
 os_io.c     getrandom(), /proc/random, time(), sockets, files  (the only OS-specific file)
```

## Using it

```c
#include <tls.h>
tls_ctx *ctx = tls_ctx_new();
tls_ctx_load_default_ca(ctx);                              /* /etc/ssl/certs/ca-bundle.pem */
tls_config cfg = { .server_name = "example.org", .alpn = "http/1.1", .ctx = ctx };
int err;
tls_conn *c = tls_connect_fd(sockfd, &cfg, &err);          /* handshake on a connected TCP socket; NULL and err on failure */
tls_write(c, request, n);  long got = tls_read(c, buf, sizeof buf);    /* got == 0: the server said close_notify */
tls_close(c);                                              /* sends close_notify, frees; the descriptor stays open */
```

`tls_new` + `tls_handshake` + `tls_get_info` give the details (protocol, cipher, key exchange group, the server's subject,
issuer, dates and fingerprint, the alert the server sent, the error that `TLS_F_NO_VERIFY` overrode, and `tls_error_where`,
the source line that raised the first error). `tls_config.flags` has `TLS_F_NO_VERIFY`, `TLS_F_TLS12_ONLY`, `TLS_F_TLS13_ONLY`,
`TLS_F_WEAK_RANDOM`, `TLS_F_NO_AESNI`; `tls_config.suites` restricts the ciphers; `.now` and `.random` replace the clock and the
random numbers (the host tests use them). `fetch`: `-k`, `-v`, `--cacert FILE`, `--tls12`, `--tls13`, `--cipher aes128|aes256|chacha20`,
`--weak-random`, `--soft-aes`, `SSL_CERT_FILE`; exit status 5 means "could not make a safe TLS connection".

## What is implemented

| Area | Done |
|------|------|
| TLS 1.3 (RFC 8446) | full client handshake; key exchange x25519 (first flight), P-256 and P-384 (after a HelloRetryRequest, cookie echoed); `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`; certificate signatures ecdsa_secp256r1_sha256, ecdsa_secp384r1_sha384, rsa_pss_rsae_sha256/384/512; middlebox compatibility mode; KeyUpdate in both directions; NewSessionTicket ignored; ALPN and SNI; a CertificateRequest is answered with an empty Certificate |
| TLS 1.2 (RFC 5246, 5289, 7905, 7627) | ECDHE-ECDSA and ECDHE-RSA with AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305; groups x25519, P-256, P-384; extended master secret when the server has it (the classic derivation otherwise: there is no resumption and no renegotiation for the triple-handshake attack to use); the TLS 1.3 downgrade marker in ServerHello.random is checked |
| Certificates | strict DER; RSA (2048 bits or more below the root) and ECDSA P-256/P-384 keys; sha256/384/512WithRSA and ecdsa-with-SHA256/384/512 signatures, SHA-1 and MD5 refused; validity; basicConstraints (CA flag, pathLen), keyUsage, extendedKeyUsage (serverAuth); subjectAltName DNS names with wildcards (a whole left-most label only, at least two labels after it) and IPv4 addresses, no Common Name fallback; unknown critical extensions fail closed; chain building with backtracking over the certificates the server sent (order does not matter, extras are ignored, cross-signed intermediates work); AKI/SKI as a filter; a server certificate that is itself in the trust store is trusted as it is |
| Primitives | SHA-256/384/512, HMAC, HKDF, the TLS 1.2 PRF, ChaCha20-Poly1305, AES-128/256 (AES-NI, or portable), GCM (PCLMULQDQ, or a bit-serial constant-time GHASH), big numbers with Montgomery arithmetic up to 4096 bits, X25519, P-256/P-384 (complete projective formulas, windowed scalar multiplication with masked table lookups), ECDSA verification, RSA PKCS#1 v1.5 and PSS verification (the expected padding is rebuilt and compared, not parsed) |
| Constants | the SHA-512 round constants, the curve parameters and the AES S-box are generated by `tools/gen_tls_tables.py` (from first principles and OpenSSL's curve dump), not typed in |

## What is not implemented

Client certificates; session resumption, tickets, 0-RTT, PSK; renegotiation (a HelloRequest is refused with `no_renegotiation`);
revocation of any kind (CRL, OCSP, stapled responses are not even requested); Certificate Transparency; name constraints and policy
processing (a *critical* extension of that kind makes the certificate unacceptable, which is the safe side); fetching a
missing intermediate certificate from the Authority Information Access URL (so a server that forgets to send its intermediate,
like `incomplete-chain.badssl.com`, is refused where a browser would manage); Ed25519/Ed448 and P-521 keys and signatures
(one root in Mozilla's list, e-Szigno TLS Root CA 2023, uses P-521 and is left out of the bundle); RSA-PSS keys and
RSASSA-PSS-signed certificates; DSA; CBC cipher suites, RSA key exchange, finite-field Diffie-Hellman, anything with RC4,
3DES, SHA-1 or export strength; compression; post-quantum hybrid groups (servers fall back to x25519); Encrypted Client Hello;
IPv6 literals in names (the stack has no IPv6); internationalised names beyond comparing the ASCII form; TLS records
larger than 16 KiB of plaintext; handshake messages larger than 160 KiB.

## Random numbers (read this)

TLS needs unpredictable keys, a ClientHello random and a session id. libtls takes them from `getrandom()` (the kernel's
`kernel/lib/random.c`; `/proc/random` shows its state). What the kernel provides:

* A ChaCha20 generator with fast key erasure (every request is served from a keystream whose first 32 bytes become the next key),
  so its output may be published (the ClientHello random is) and a later memory compromise does not reveal earlier outputs.
  The generator it replaced, xoshiro256**, would have leaked its whole state through four ClientHello randoms.
* Seeding at boot: `RDSEED` (credited in full, 256 bits for four draws) and `RDRAND` (credited at half) when CPUID says they
  exist, plus 64 TSC samples after short uneven busy-waits (credited at a quarter bit each: 16 bits) and, from then on, events
  (keystrokes, mouse packets) stirred in at a quarter bit each; the key is re-mixed every 64 events or five minutes, with fresh
  RDRAND and TSC. "Ready" means 128 estimated bits.
* **On a CPU without RDRAND/RDSEED (before Ivy Bridge, 2012, or an emulator's default `qemu64` model) the seed is little more than
  boot-time timing**, which someone who can guess the boot time to the millisecond could enumerate. `/proc/random` then says
  `ready: no`, and libtls **refuses to connect** (`TLS_E_ENTROPY`; `fetch` says so and exits with status 5) until the estimate
  reaches 128 bits or the caller passes `TLS_F_WEAK_RANDOM` (`--weak-random`). The estimate is a heuristic: timing jitter inside a
  virtual machine can be far more regular than a quarter bit per sample, so even a "ready" VM without RDRAND deserves suspicion.
* The real target (an i5-7500, Kaby Lake) has both instructions. QEMU's TCG emulates them with the host's randomness, so the
  hardware path has run on emulated and not on real silicon.

## Security notes (honest)

* **No side-channel guarantees.** The code is written to avoid secret-dependent branches and table lookups: comparisons use
  `tlsc_ct_memeq`; ChaCha20, Poly1305, SHA-2, the Montgomery field arithmetic, the X25519 ladder (masked swaps) and the ECDH scalar
  multiplication (fixed windows, masked table lookups, complete addition formulas) have fixed control flow; the AES-NI/PCLMULQDQ
  path touches no tables. But it is C compiled with `-O2`, the compiler may turn a mask back into a branch, and nobody has looked
  at the machine code with a timing-leak tool or run it on a CPU with a known side channel. Treat it as "not obviously leaky".
* **The portable AES is not constant time.** Without AES-NI it indexes a 256-byte S-box with secret data (cache-timing leak).
  libtls offers ChaCha20-Poly1305 first on such CPUs, but a server that only does AES-GCM gets the table-based code. A
  bit-sliced AES would fix that; it is not written.
* ECDSA and RSA are only ever *verified* (public inputs, variable time is fine). `tlsc_mont_pow` and `tlsc_mont_inv` branch on the
  bits of their exponent and may only be given public exponents (RSA's `e`, the field prime minus two).
* Key material is wiped with a volatile loop when a connection ends, but copies in dead stack frames may remain, and
  `tls_conn` itself (with the traffic secrets, needed for KeyUpdate) lives until `tls_close`.
* **Verification is only as good as the clock and the bundle.** Validity uses `time()`; with a wrong clock chains fail (or, worse,
  pass). Set it with `sntp -s`. The bundle is Mozilla's list as of the day the system was built (`tools/mkcabundle.py`,
  currently 119 roots from certifi 2026.10.19) and nothing updates it, so a root that Mozilla distrusts later stays trusted here.
* `-k` / `TLS_F_NO_VERIFY` still checks that the server holds the private key of whatever certificate it sent (the handshake
  signature), but any certificate will do: it protects against passive eavesdroppers only. `fetch -k` says so every time and says
  what would have been refused.
* A connection that ends without `close_notify` is reported (`TLS_E_TRUNCATED`) because the data may have been cut short.
  `fetch` accepts that when a `Content-Length` or a final chunk shows that the message is complete (several big sites close
  that way), and fails it otherwise.
* Nothing here has been fuzzed beyond the fault tests below, nor reviewed by anyone but the author. Do not rely on it for secrets
  you would not send over plain HTTP in a test.

## Trust store

`python tools/mkcabundle.py` writes `initrd/Hakurei/etc/ssl/certs/ca-bundle.pem` (about 180 KB as PEM) from the `certifi` package
(Mozilla's list). Without `certifi` it exports the Windows "ROOT" store filtered to server-authentication roots and says that this
is Microsoft's list. It keeps RSA and P-256/P-384 roots that have not expired, merges duplicates, sorts by name, and reads the
result back through libtls to prove that all of it loads. Regenerate and rebuild to refresh. `tests/case_tls.py` checks that
every root loads and that, apart from the SHA-1 signed ones (which are fine as trust anchors, their own signature is never
checked), each root verifies its own signature, which exercises RSA and ECDSA on real certificates.

## Tests

The C sources are compiled a second time, freestanding, for the build machine (`python tools/tlshost.py` builds
`build/tlshost/tlshost.dll`; `tools/tlshost/hostlib.c` supplies `mem*`, `str*` and a bump `malloc`), and Python drives them through
`ctypes` (`tests/tlslib.py`, `tests/tlskat.py`). So the crypto and the protocol are tested against `cryptography`, `hashlib` and
OpenSSL (Python's `ssl` module as the server; `openssl s_server` for KeyUpdate) without booting QEMU. `pip install cryptography`
is needed; without it the tests print `SKIP`.

| Test | What it proves |
|------|----------------|
| `tls_host_kat_symmetric` | SHA-2, HMAC, HKDF, ChaCha20, Poly1305, ChaCha20-Poly1305, AES (AES-NI and portable) and GCM against hashlib/cryptography and the RFC vectors; flipped bits in tag, ciphertext and AAD are refused |
| `tls_host_kat_public_key` | big numbers (random moduli of 64 to 4096 bits, extremes), X25519 (RFC 7748 vectors incl. the 1000-iteration one, low-order points rejected), P-256/P-384 key pairs, ECDH and ECDSA against cryptography, off-curve and compressed points, r = 0, s = n, ... ; RSA PKCS#1 v1.5 and PSS at 1024 to 3072 bits |
| `tls_host_handshakes` | against OpenSSL: every TLS 1.3 cipher with AES-NI and portable AES, EC/RSA leaf under EC/RSA roots, all six TLS 1.2 suites, HelloRetryRequest to P-256 and P-384, ServerKeyExchange with those curves, ALPN, 3 MB echoed both ways in 1.3 and 1.2 |
| `tls_host_key_update` | `openssl s_server` rolls its keys (with and without asking for ours); data keeps flowing in both directions (skipped if no pipe-friendly `openssl` is found) |
| `tls_host_certificates` | wrong name, expired, not yet valid, unknown CA, self-signed, client-only EKU, in TLS 1.3 and 1.2; the same with `TLS_F_NO_VERIFY` (connects, remembers the reason); intermediates, a forgotten intermediate, unrelated extras, pathLen 0 violated, an intermediate without the CA flag, a pinned server certificate, IP address SANs |
| `tls_host_names` | wildcard and SAN matching rules (26 cases) |
| `tls_host_faults` | through a record-aware proxy: bit flips in the encrypted handshake and in data (TLS 1.3 and 1.2), the connection cut after 1, 2, 3 server records, close without `close_notify`, a fatal `protocol_version` alert, plain HTTP and random garbage and a record header claiming 64 KiB where TLS was expected, a forged downgrade marker, a modified ServerHello |
| `tls_host_roots` | the shipped bundle loads completely and its roots verify their own signatures |
| `tls_guest_fetch` | in the system: `fetch -v --cacert` over TLS 1.3 (all three ciphers, with and without `--soft-aes`) and 1.2 (RSA certificate), SNI seen by the server, name resolution through `/etc/hosts`, `wget` saving a file, redirects http to https and https to http, a pinned certificate, the default bundle refusing the test CA (status 5), `SSL_CERT_FILE` |

Also tried by hand from the host DLL against about 35 live sites (example.com, Google, GitHub, Cloudflare, Wikipedia, Amazon,
Microsoft, Let's Encrypt, Apple, Mozilla, DuckDuckGo, Reddit, python.org, ietf.org, Stack Overflow, Hacker News, Akamai's TLS 1.3
test host, the `badssl.com` family): all worked except where the server was meant to be refused. Sites that close without
`close_notify` exist (Google does); some CDNs reset connections now and then (Python's own `ssl` sees the same).
A QEMU guest fetches a 580 KB page from github.com in about a second of wall time.

## How to resume

1. `python tools/build.py`, then on the build machine (needs `pip install cryptography`; Git for Windows' `openssl` for the
   KeyUpdate test): `python tests/run_all.py tls_host` (about 15 s).
2. `python tests/run_all.py tls_guest` (about 100 s; the last one needs internet and skips itself otherwise).
3. `python tests/run_all.py manual,net,apps` and finally the whole suite; fix what the `fetch` rewrite, the 180 KB bundle or the
   unverified page syntax broke. The kernel commit `361314b` ("NETCTL_DHCP_STOP, /proc/net/dhcp ...") is separate and can be
   reverted alone.
4. Debugging a handshake: `fetch -v URL` prints the details; `tls_error_where()` says which source line raised the error; the host
   DLL (`tests/tlslib.py`: `Client`, `Server`, `Proxy`) reproduces most things in seconds, and `python tools/tlshost.py --force`
   rebuilds it after a source change. Every `.c` file under `user/lib/tls/src` except `os_*.c` goes into the DLL automatically.
5. Refresh the roots: `python -W ignore tools/mkcabundle.py`, rebuild, `python tests/run_all.py tls_host_roots`.
