# Block devices: AHCI (SATA) and NVMe

Two polled storage drivers sit under the block layer (`kernel/include/blk.h`, `kernel/drivers/blk.c`): **ahci** registers SATA
disks as `sda`, `sdb`, ... and **nvme** registers NVM Express namespaces as `nvme0n1`, `nvme0n2`, `nvme1n1`, ... . The block
layer adds `/dev` nodes, scans GPT/MBR into partition children (`sda1`, `nvme0n1p2`) and lists everything in `/proc/partitions`
(`lsblk`). They were written for the owner's real PC (a Dell with an Intel Kaby Lake PCH: M.2 NVMe SSD most likely, SATA
possible) and verified against QEMU's `ich9-ahci` and `nvme` models.

| File | What it is |
|------|------------|
| `kernel/drivers/ahci.c` | strong `ahci_init()`: HBA bring-up, ports, IDENTIFY, READ/WRITE DMA EXT, FLUSH, error recovery |
| `kernel/drivers/nvme.c` | strong `nvme_init()`: controller bring-up, admin and I/O queues, namespaces, PRPs, sliding window of commands |
| `kernel/drivers/blkdrv_util.h` | shared helpers: MMIO access, `BLK_POLL` (spin, then sleep), physical-run splitting, identify strings, `sd_name` |
| `kernel/drivers/blk_selftest.c` | optional in-kernel I/O check driven by `blkselftest=` on the command line (used by the tests) |
| `tests/case_blockdev.py` | 21 QEMU tests, images generated by the test itself |

Nothing outside these files was changed: `kmain()` already called the weak `ahci_init` / `nvme_init`.

## What you see in the log

All driver messages carry the `Kappa` tag (hardware). A healthy boot of a PC with one NVMe SSD looks like:

```
[Kappa] ahci0: 8086:a102 at 00:17.0, AHCI 1.3.1, 3 of 6 ports implemented, 32 command slots, 64-bit DMA, NCQ (unused)
[Kappa] ahci0: probed in 3 ms: 0 disks, no device on port 0 1 2
[Kappa] nvme0: 144d:a808 at 03:00.0, NVMe 1.3, up to 16384 queue entries, doorbell stride 4, ready timeout 7500 ms
[Kappa] nvme0: "SAMSUNG MZVLB256HAHQ-000L7" serial S4ABNX0K123456 firmware 4L2QEXA7, namespace ids up to 1, max transfer 128 KiB per command, volatile write cache (flushed after every write)
[Kappa] nvme0: nsid 1: 244198 MiB, 500118192 blocks of 512 bytes
[Marisa] blk: nvme0n1  nvme  244198 MiB, 512-byte sectors  SAMSUNG MZVLB256HAHQ-000L7
[Marisa] blk: nvme0n1p1  100 MiB  start 2048  label EFI system partition
```

(illustrative; the numbers are from a typical laptop, not from the owner's machine). `dmesg | grep -E 'ahci|nvme|blk'` shows
the lot; `cat /proc/ahci` and `cat /proc/nvme` show the controllers with per-port / per-controller counters (`cmds`, `errors`,
`resets`, `flushes`, and `DEAD` once a device has been given up on); `lspci -v` shows which PCI function each driver claimed.

### A disk does not show up: what the log says

| You see | It means | What to do |
|---------|----------|------------|
| no `ahci` and no `nvme` line at all | no controller with the right PCI class was found | `lspci`: is there a `0106:01` (AHCI) or `0108:02` (NVMe) entry? If only `0104` / `0101` entries exist, read the next two rows |
| `SATA controller is in RAID (Intel RST) mode: switch it to AHCI in the BIOS setup to use its disks` | Intel RST / RAID mode: the SATA controller shows up as PCI class `0104` and an NVMe drive in the M.2 slot is hidden behind it (remapped, not visible as a PCI device) | BIOS setup: *System Configuration > SATA Operation > AHCI* (see below) |
| `Intel SATA controller is in legacy IDE mode: switch it to AHCI ...` | the BIOS exposes the SATA ports through the old IDE interface (`0101`) | same BIOS setting |
| `nvme: no NVMe controller is visible, but the Intel SATA controller at ... is in RAID (Intel RST) mode` | the NVMe drive is the one hidden by RAID mode | same |
| `ahci0: probed in N ms: 0 disks, no device on port 0 1 2` | the HBA works, no port reports a device (`PxSSTS.DET` = 0) | is the drive in the other bay / the M.2 slot a SATA one? is the port disabled in the BIOS (*System Configuration > Drives*)? |
| `ahci0 port N: a device is attached but did not come up (SSTS 0x..., TFD 0x...)` | link negotiation or the device's power-on is stuck. `SSTS` low nibble is DET (1 = presence only, 3 = link up), next nibble the speed, third nibble IPM (1 = active, 2/6 = partial/slumber). `TFD` bit 7 is BSY | power-cycle the machine; try another cable / port |
| `ahci0 port N: IDENTIFY DEVICE failed (...)` | the link is up but the disk does not answer | same; check `errors`/`resets` in `/proc/ahci` |
| `ahci0 port N: ATAPI device (CD/DVD) -- not supported, ignored` | an optical drive | expected |
| `... has no 48-bit LBA support` / `uses N-byte logical sectors` | an old (pre-2003) disk, or a disk with unusual sector size | not supported |
| `ahci0 port N: the disk is ATA-security locked` | an ATA password is set and the BIOS did not unlock the disk | unlock it from the BIOS / `hdparm` elsewhere |
| `ahci0 port N: command XX (lba L, C sectors) failed: ... IS 0x... TFD 0x... SERR 0x...` | a command failed; the driver reset the link and returns `-EIO` | `TFD` bits 15:8 are the ATA error register (bit 2 ABRT, bit 6 UNC = unreadable sector, bit 7 ICRC = cable/CRC) |
| `... giving up on this disk` / `the disk did not come back after a link reset` | unrecoverable; requests fail fast from now on | reboot |
| `nvme0: the controller did not become ready (CSTS 0x...)` / `does not stop` | the controller never reached `CSTS.RDY` (bit 0) in `CAP.TO` x 500 ms (2 s minimum); `CSTS` bit 1 is CFS (fatal) | power-cycle; try another M.2 slot |
| `nvme0: ... failed: status type T code 0xNN` | the controller rejected a command (T = status code type: 0 generic, 1 command specific, 2 media error) | T=2 code 0x81 is an unrecovered read error |
| `nvme0: I/O command timed out (CSTS ...); giving up on this controller` | a command never completed; the controller was disabled so it cannot DMA into reused memory, every later request returns `-EIO` | reboot |
| `nvme0: nsid N is formatted with M bytes of metadata per block -- not supported, skipped` | the namespace uses an LBA format with metadata (rare; consumer drives ship with plain 512 or 4096) | reformat the namespace to a metadata-free LBA format elsewhere |
| `nvme0: the controller needs memory pages larger than 4 KiB` | `CAP.MPSMIN` > 0 (Apple controllers) | not supported |

## How the block layer sees them

* `BlockDev.name`: `sda`..`sdz`, `sdaa`.. (Linux scheme) in port order, controllers in PCI enumeration order; `nvme<controller>n<NSID>`
  (the namespace id, as Linux names single-path namespaces, so nsid 1 and 3 give `nvme0n1` and `nvme0n3`).
* `BlockDev.model`: the IDENTIFY model / Identify Controller model, trimmed. `driver` is `"ahci"` or `"nvme"`.
* `sector_size` is 512 or 4096 (logical size; 512e disks are 512). Other sizes are refused.
* Buffers may be anywhere in the direct map or the kernel image and need not be aligned. **Nothing above 4 GiB is ever handed to a
  controller:** the drivers' own memory (command lists, FIS areas, queues, PRP lists, identify and bounce buffers) comes from
  `dma_alloc_low`, a `dma_alloc` block that is checked to lie below 4 GiB (it is simply refused otherwise), and a caller's buffer is used for
  DMA only when every byte of it is below 4 GiB (and, for AHCI, 2-byte aligned; for NVMe, 4-byte aligned); anything else is copied through
  a 128 KiB bounce buffer in chunks. The rule is the same whatever the controller claims: an AHCI controller with `CAP.S64A = 0` (32-bit DMA only)
  is driven exactly like a 64-bit one (its `PxCLBU/PxFBU` registers, reserved on such a controller, are not written), and the 64-bit
  capability is never used. `/proc/ahci` and `/proc/nvme` count the bounced transfers (`bounced`).
* Any `count` is accepted and split inside the driver. Several threads may call at once (one mutex per AHCI port, one per
  NVMe controller); `/dev/<disk>` byte access goes through `blkdev_io`, which issues at most 64 KiB per call, so only
  filesystems and the in-kernel check ever ask for more.
* **Write policy:** every write request is followed by a flush before it returns (SATA: whenever the disk has a flush command, since a link
  reset puts a disk's write-cache setting back to its default; NVMe: when the controller reports a volatile write cache). One flush per request
  however large. The reason is practical: nothing above the block layer flushes yet (`sync` is a no-op, power-off and reset do not flush),
  and the machine is an ordinary PC whose SSD loses its cache on power loss. `ahci.nosync` / `nvme.nosync` turn it off.

## Safety guarantees for a real disk

* **The drivers never write on their own initiative.** Bring-up and probing send only: AHCI link/port register operations (COMRESET, spin-up,
  engine start/stop), IDENTIFY DEVICE and, when a command fails, link resets; NVMe controller enable/disable, Identify (controller, namespace
  list, namespace), Set Features *Number of Queues*, Create I/O Queue. The only commands that move data are READ and WRITE issued from
  `BlockDev.read/write`, and FLUSH issued after a write or by `blk_flush`. There is no Format, Sanitize, Security Erase/Unlock, TRIM / Dataset
  Management, Write Zeroes, SET FEATURES (write cache) or any other media-changing command anywhere in the code.
* A write command exists on the wire only if somebody called `blk_write` (or `BlockDev.write`). Callers are: a filesystem on a mounted block device,
  and root writing to a `/dev/<disk>` node (mode 0600, as `blkdev_io` has always allowed). Partition scanning (GPT/MBR) only reads.
* **`blk.ro` on the kernel command line** (cmdline.txt) registers every SATA disk and NVMe namespace read-only: `blk_write` returns `-EROFS` before
  the driver is reached, partitions inherit it, `lsblk` shows `RO 1`. The first boot on the owner's PC should use it (tested by `blk_readonly_switch`).
* The in-kernel check `blkselftest=<dev>:rw` is the only code in the drivers' files that overwrites a device on purpose. It needs that explicit
  command-line word, and before it writes anything it reads the device and compares it with the test pattern; a device that does not hold the
  pattern (any real disk) makes it log `refusing to write to it` and stay read-only.
* An ATA-security-locked disk is reported and left locked; nothing here tries to unlock, freeze or erase it.

## AHCI driver

Bring-up of a controller (`hba_probe`):

1. PCI class `01:06:01`; memory + bus master enabled (INTx stays off), ABAR = BAR5 mapped uncached. A controller that reads all ones is skipped.
2. **BIOS/OS handoff** when `CAP2.BOH` is set and the BIOS owns the semaphore: set `BOHC.OOS`, wait 25 ms for `BOS` to clear, up to 2 s if the BIOS is busy.
3. `GHC.AE = 1`, `GHC.IE = 0` (no HBA interrupts), pending `IS` cleared. If `PI` reads 0 the first `CAP.NP+1` ports are assumed.
4. **No reset unless needed.** The firmware's configuration is kept. Every implemented port's command engine is stopped
   (`ST` cleared, wait for `CR`; then `FRE`, wait for `FR`, 500 ms each as the spec allows). Only if one refuses to stop is the HBA reset
   (`GHC.HR`, `PI` restored) once. (Linux resets every time; `ahci.hbareset` forces our reset path for testing.)
5. **Detect** on every port (registers only, so empty ports cost nothing): `PxSCTL.IPM = 3` (no partial/slumber), `ALPE`/`ASP` and device-sleep
   cleared, stale `SERR`/`IS` cleared, `SUD`/`POD` set if the port was unpowered. A port with `DET = 0` that we just powered gets one
   shared 500 ms moment to answer; everything else is judged immediately.
6. **Bring-up** in port order for ports with a device: one `dma_alloc_low` block (command list 1 KiB-aligned, received-FIS area, identify
   buffer, command table with 256 PRD entries; about 8 KiB), `PxCLB/PxFB` programmed, `FRE` on (the device's signature FIS needs somewhere to land),
   link check: `DET = 3` and `IPM = 1` (a sleeping link gets `ICC = active`; anything else one COMRESET: `DET = 1` for 2 ms, 200 ms settle, then
   `DET = 3` must hold for 100 ms within 2 s, as libata does), wait up to 20 s for `BSY`/`DRQ` to clear (a second COMRESET if not), signature check
   (`0xEB140101` ATAPI, `0x96690101` port multiplier, `0xC33C0101` enclosure bridge are logged and skipped), `ST` on (command list
   override first if `BSY`/`DRQ` are stuck and `CAP.SCLO`), IDENTIFY DEVICE (a second attempt follows the link reset a failure causes).
   A port whose `SCTL.DET` is 4 (interface switched off by the firmware) is left alone. After an HBA reset every port is given up to 2 s
   to renegotiate its link before it is judged empty.
7. IDENTIFY parsing (`ata_parse_identify`, a pure function with its own check, `ahci.selftest`): ATA string byte order, LBA48 capacity
   from words 100-103, **logical sector size** from words 106 and 117-118 (4Kn = 4096; 512e keeps 512 and is only reported),
   flush command (FLUSH CACHE EXT / FLUSH CACHE) from word 83, write cache on/off from words 85/87, SSD from word 217,
   ATA security lock from word 128. Disks without LBA48 are refused.

I/O (`ahci_rw`): one command slot per port, so one command in flight; the mutex serializes callers. A request is split into commands of
at most 4 MiB and 65535 sectors. Each command is READ/WRITE DMA EXT with a PRDT built from the buffer's physically contiguous runs
(up to 4 MiB per entry, 256 entries; if the table fills mid-sector the tail is trimmed to whole sectors), or goes through a 128 KiB
bounce buffer. Completion is polled: ~100 us of spinning, then 1 ms sleeps, until `PxCI` bit 0 clears (15 s; flush 30 s; identify 5 s).

Errors: `PxIS` bits TFES (task file error), HBFS, HBDS, IFS, OFS, a set `ERR`/`DF` in `PxTFD`, or a timeout all mean *the command
failed*: the port is logged, the engine stopped (`ST` clear, wait `CR`), `SERR`/`IS` cleared, COMRESET, wait up to 10 s for `BSY` clear,
engine restarted. A timeout, an interface/host-bus error or a UDMA CRC error from the disk is then retried (twice at most); media and
command errors (UNC, ABRT, IDNF) are not, they return `-EIO` at once. If the disk does not come back the port is marked dead and every later
request fails immediately. If the engine will not stop even after the port reset, the whole controller is reset and bus mastering is
switched off (`hba_halt`), because a running engine could still finish the abandoned command into a buffer the caller is about to free; all
ports of that controller are then dead. A port that will not idle during a teardown keeps its memory (leaked on purpose).

Not done: NCQ, interrupts, hot-plug, port multipliers, ATAPI, link power management, TRIM, SMART, 28-bit-only disks, FIS-based switching,
aborting a single command, drives below 512-byte logical sectors.

## NVMe driver

Bring-up of a controller (`ctrl_probe`):

1. PCI class `01:08:02`; BAR0 (64-bit memory BAR) mapped uncached. `CAP` is read in two 32-bit halves: `MQES`, `TO` (500 ms units, 2 s minimum), `DSTRD` (doorbell stride), `CSS` (NVM command set needed), `MPSMIN` (must be 0: 4 KiB pages).
2. **Disable**: `CC.EN = 0` whatever the firmware left, wait for `CSTS.RDY = 0`.
3. Admin queue pair (16 entries, `dma_alloc_low` memory), `AQA`/`ASQ`/`ACQ`, then `CC` = NVM command set, 4 KiB pages, round robin, `IOSQES = 6`,
   `IOCQES = 4`, `EN = 1`, wait for `RDY` (a set `CFS` ends the wait).
4. **Identify Controller**: model, serial, firmware, `MDTS` (max transfer = 4 KiB << MDTS, capped at 128 KiB here), `VWC`, queue entry sizes.
5. Set Features *Number of Queues* (1+1), then **Create I/O Completion Queue, then Create I/O Submission Queue** (128 entries or `MQES+1`,
   physically contiguous, interrupts off).
6. **Namespaces**: Identify *Active Namespace ID list* (CNS 2; if the controller does not know it, namespace 1 is tried), then Identify
   Namespace for each: `NSZE`, the current LBA format from `FLBAS` (`LBADS` 9 or 12 only), metadata size and protection information must
   be zero (otherwise skipped with a log line). Each usable namespace becomes `nvme<c>n<nsid>`.

I/O (`rw_direct`): the I/O queue pair is shared by all namespaces of a controller. A request is cut into commands of at most 128 KiB
(or MDTS). Up to 16 commands are kept in flight (command id = window slot, each slot owns one page for its PRP list): submit while there
is room and ring the SQ doorbell once, wait for a completion (phase tag), reap everything that is ready, ring the CQ doorbell once, repeat.
PRP1 carries the page offset, PRP2 is the second page or a PRP list. A completion with a non-zero status field is logged (`SCT`/`SC`,
do-not-retry bit) and fails the request with `-EIO` after the commands already in flight have drained (their PRPs point into the caller's
buffer); unaligned buffers (not dword aligned) go through a 128 KiB bounce buffer. Wait limits: 15 s per I/O completion, 30 s for a flush,
15 s per admin command.

A completion with the do-not-retry bit clear is resubmitted up to three times (2 ms apart) before the request fails, as Linux does.

Fatal handling: `CSTS.CFS`, a timeout, a completion for a command that is not in flight, or a failed admin command during bring-up make the
driver log the reason, clear the PCI bus-master bit (a function that may not master the bus cannot DMA, whatever its firmware does), write
`CC = 0`, wait up to `CAP.TO` for `RDY = 0`, and mark the controller dead; every later request returns `-EIO` at once, including requests that
were already waiting for the queue lock. There is no controller reset-and-continue. A controller the firmware left enabled but not yet ready
is given time to finish before `CC.EN` is cleared; `CAP.TO` is used unclamped (2 s minimum); controllers older than NVMe 1.1 are scanned
namespace by namespace instead of through the id list.

Not done: interrupts and MSI-X, more than one I/O queue (a single CPU), hot-plug, namespaces with metadata or protection information, TRIM
(Dataset Management), controller shutdown notification (`CC.SHN`: there is no shutdown hook in the kernel yet, hence the flush after
every write), Host Memory Buffer, power states, controllers with larger-than-4-KiB pages, multi-path / shared namespaces, abort.

## Real hardware notes

**Intel RST / RAID mode is the thing to check first.** Dell ships many laptops with *SATA Operation = RAID On* (Intel Rapid Storage
Technology). In that mode the PCH's SATA controller identifies as PCI class `0104` (RAID) instead of `0106` (AHCI), it belongs to Intel's
RST driver (RAID volumes, caching), and an NVMe SSD in the M.2 slot is **not enumerated as a PCI device at all**: it is remapped into the
SATA controller's register space. Linux has the same limitation for the NVMe drive and tells you to switch the BIOS to AHCI. This driver
deliberately does not touch a RAID-mode controller (a RAID member driven as a plain disk would be mutilated) and only logs the hint. So on this PC:

1. In the BIOS setup (F2 at power-on): *System Configuration > SATA Operation*, choose **AHCI** (the choices are typically *Disabled / AHCI /
   RAID On*; newer machines say *Intel RST Premium with Intel Optane System Acceleration* for RAID). In AHCI mode the NVMe drive appears as an
   ordinary PCI function (class `0108:02`) and SATA drives behind the AHCI controller (class `0106:01`). *System Configuration > Drives* lists
   `SATA-0` and `M.2 PCIe SSD-0` and can disable them individually.
2. **Windows warning**: an existing Windows install that was set up in RAID mode usually stops booting (`INACCESSIBLE_BOOT_DEVICE`) after
   that switch because its AHCI driver is not loaded at boot. The known sequence is: in Windows run `bcdedit /set {current} safeboot minimal`,
   reboot into the BIOS, switch to AHCI, boot (Windows comes up in safe mode and loads the driver), then `bcdedit /deletevalue {current} safeboot`
   and reboot. Back up first. This is the owner's call; TouhouOS cannot read the disk in RAID mode at all.

Other things worth knowing:

* The driver is **polled**: it never touches interrupt routing (IOAPIC, `_PRT`, MSI), the most fragile part of real PCs. PCI INTx is disabled
  for both controllers; the AHCI `GHC.IE` is cleared; NVMe queues are created without interrupts. Idle cost is zero (no background thread).
* `AHCI` ports and `NVMe` controllers the firmware has already initialised are handled: the engine is stopped before the lists are replaced,
  the NVMe controller is disabled before its queues are replaced. **Known gap, outside these files:** the loader hands the firmware's
  `EfiBootServicesData` memory to the allocator as free RAM (`boot/main.c`), and the drivers only run in `kmain` after `pci_init`; between
  `ExitBootServices` and `ahci_init` / `nvme_init`, a controller the firmware left running could still write a FIS or completion into pages that
  were already reused (only if the device sends something unsolicited, such as an NVMe asynchronous event; reference firmware is not known to
  leave anything outstanding, but the Dell firmware is an unknown). Closing it needs
  an earlier quiesce step (clear bus mastering of class 01 devices right after `ExitBootServices`, or keep those regions reserved until the drivers ran).
* Link power management is left off on purpose (`IPM = 3`, `ALPE` cleared). NVMe power states (APST) are not touched; the drive stays in
  whatever state the firmware left it (usually fully on).
* Some Dell models also expose a second M.2 slot or a SATA bay that is simply empty: those ports show up in the `no device on port` list.
* On real silicon the first things to look at are the three `Kappa` lines per controller (found / identified / sized) and `/proc/ahci`,
  `/proc/nvme`. Reads are safe to try first: `dd if=/dev/nvme0n1 bs=512 count=1 | xxd | head` (the GPT header is in the second sector:
  `bs=512 skip=1 count=1`), `cat /proc/partitions`, `dd if=/dev/nvme0n1 of=/dev/null bs=1M count=256` for a speed number. **Do not write
  to the internal disk from the shell** (`dd of=/dev/...`) unless that is the intent: root writes go straight to the device.
* Untested here because QEMU cannot present them: the RAID-mode hint, the BIOS handoff, a 4Kn SATA disk (the identify words are checked with
  hand-made blocks), staggered spin-up, a sleeping link, port multipliers, NVMe controllers that reject the Number of Queues feature.

## Kernel command line knobs

These exist so the tests can reach paths that QEMU never takes by itself. They are harmless to leave out; nothing here is needed for normal use.

| Knob | Effect |
|------|--------|
| `blkselftest=<dev>[:rw],...` | after the owning driver registered `<dev>`, run the in-kernel I/O check on it (needs the pattern image made by `tests/case_blockdev.py`; `:rw` overwrites the device) |
| `ahci.selftest` | check the IDENTIFY parser with hand-made blocks (4Kn, 512e, no LBA48, ATAPI, locked, write cache) |
| `ahci.maxsect=N` `ahci.prdlen=N` `ahci.prdmax=N` | at most N sectors per command / N bytes per PRD entry / N PRD entries per command |
| `ahci.bounce` `ahci.hbareset` `ahci.nosync` | always bounce / reset the HBA at start / no flush after writes |
| `ahci.iotimeout=ms` `ahci.dropcmd=N` | read/write timeout / never issue the N-th read or write (it then times out for real) |
| `nvme.maxxfer=N` `nvme.window=N` `nvme.depth=N` | bytes per command / commands in flight / I/O queue entries (tiny values force queue wrap-around) |
| `nvme.bounce` `nvme.nosync` | always bounce / no flush after writes |
| `blk.ro` | register every disk these drivers find read-only (**use this for the first boot on real hardware**) |
| `blk.dmalimit_mb=N` | test only: treat caller memory above N MiB as unreachable for DMA (stands in for 4 GiB; forces the bounce path for buffers up there) |
| `nvme.iotimeout=ms` `nvme.dropcmd=N` | completion timeout / never ring the doorbell for the N-th read/write batch |

## Tests

`python tests/run_all.py blk_` runs the 21 block tests (about 4 minutes); `python tests/run_all.py` runs everything (35 tests). All
images are generated under `build/blkdev/` by `tests/case_blockdev.py`: every 512-byte block *b* of a "pattern-A" image holds the 64-bit word
`pat_a(b)` repeated, so the host can recompute any byte range, and after a VM exits the test reads the image file to see what the guest wrote.
The guest runs as root (`user=root`) because the block nodes are mode 0600.

| Test | Covers |
|------|--------|
| `blk_sata_read`, `blk_nvme_read` | log lines, model/serial/firmware, `lsblk` and `/proc/partitions` rows, whole-device sha256 against the host, unaligned byte ranges, reads that end past the device, ATAPI skipped, identify self-check |
| `blk_copy_matrix` | `dd` between SATA and NVMe in all four directions at 512 B, 4 KiB, 64 KiB and 1 MiB records plus unaligned ranges; guest read-back and host image compare; write past the end fails |
| `blk_partitions` | GPT (CRCs valid) and MBR images give `sdb1`/`sdb2`, `nvme0n1p2`, and on a 4096-byte-block namespace `nvme0n2p1`, with start, size, label, parent and data |
| `blk_parallel` | six `dd` processes (readers and writers on both drivers) at once |
| `blk_sata_errors`, `blk_nvme_errors` | injected read and write errors (QEMU `blkdebug`): `EIO`, log lines, link reset / status codes, the device keeps working, failed writes do not reach the image |
| `blk_sata_timeout`, `blk_nvme_timeout` | a lost command: AHCI port reset and recovery; NVMe controller given up, later requests fail fast, the other disks are unaffected |
| `blk_topology` | two AHCI controllers (one with a 512e disk), two NVMe controllers, namespaces 1 and 3, a namespace with metadata skipped, a 4096-byte-block namespace |
| `blk_selftest_*` (5) | the in-kernel check (many request sizes and misalignments, 16 MiB requests, writes, flush) under default settings and with tiny commands, a PRD table that runs out mid-sector, bounce buffers, a wrapping NVMe queue, and after an HBA reset |
| `blk_nvme_mdts` | the controller's own transfer limit (8 KiB) is honoured |
| `blk_write_flush` | writes are followed by flushes, reads are not, `nosync` switches it off |
| `blk_readonly_switch` | `blk.ro`: disks and partitions are read-only, writes fail, images are byte-identical afterwards |
| `blk_dma_below_4g` | with the DMA limit lowered to 48 MiB, buffers above it are bounced, the in-kernel check passes on SATA and both NVMe block sizes, `bounced` counters move |
| `blk_system_with_devices` | the kernel self test, the user-space suite and the ~150 shell checks pass with both kinds of disk attached |
| `blk_throughput` | informational MB/s (below) |

QEMU facts the tests rely on: the boot ESP is a vvfat drive on AHCI port 0, so it is always `sda` (and `sda1`); QEMU's default CD-ROM sits on
port 2 unless an `ide-hd` is configured (then it is dropped, so the SATA tests add an explicit `ide-cd`); a second `ich9-ahci` enumerates before
the built-in one (PCI slot 2 versus 0x1f), so its disks get the first letters; IDE devices cannot have 4096-byte logical sectors in QEMU, only
512e (`physical_block_size=4096`); I/O errors are injected with a `raw` driver on top of `blkdebug` (the other way round injects nothing);
`nvme-ns` with `ms=8` gives a namespace with metadata.

The tests that need a failing storage path rely on test knobs (above) or QEMU `blkdebug` rather than on timing, so they are not flaky when the
host is busy; the long ones allow generous boot timeouts.

### Throughput (informational, QEMU TCG, not hardware)

16 MiB through `/dev/<disk>` with `dd bs=1M` (64 KiB per request as issued by the block layer; writes include a flush per request) and as one
request straight into the driver (in-kernel check; guest clock). The guest clock under TCG runs slow while the vCPU sits in a long MMIO
handler, so the host wall-clock figure (includes shell start-up) is shown as well; neither is a statement about real hardware.

| Disk | `dd` read | `dd` write | driver read (16 MiB request) | driver write (16 MiB request) |
|------|-----------|------------|------------------------------|-------------------------------|
| SATA (QEMU AHCI) | 109 MB/s guest clock, 49 MB/s wall | 30 MB/s guest, 15 MB/s wall | 267 MB/s | 696 MB/s |
| NVMe (QEMU) | 95 MB/s guest clock, 41 MB/s wall | 29 MB/s guest, 20 MB/s wall | 178 MB/s | 333 MB/s |

## Limits and risks

* Everything was verified in QEMU only. The code follows the AHCI 1.3.1 and NVMe 1.4 specifications and Linux's behaviour where the spec
  leaves room (link power management off, COMRESET timings, no HBA reset by default), but a real controller will always find something new.
  The first run on the PC should be treated as a read-only experiment.
* No hot-plug, no TRIM, no NCQ, no interrupts, no power management (see the "not done" lists above). One command at a time per SATA port.
* A SATA command that times out costs a link reset and up to ~10 s; an NVMe controller that times out is gone until reboot.
* The write-through policy makes small writes slow on rotating disks (each write request waits for a cache flush); it is the price of
  not having a shutdown path that flushes.
* All DMA structures are checked to be below 4 GiB (`dma_alloc_low`; a block above it is freed and the port / controller fails to start with a log
  line), and data above 4 GiB is bounced, so 32-bit-only and quirky 64-bit controllers (some ASMedia parts) see the same low addresses.
* The existing `utest` test (signals section) fails now and then, with or without these drivers: it was seen on the untouched baseline commit as well
  (a user process dies from a signal during the `fork`/`kill` checks). It is not related to storage.
